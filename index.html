Types must reflect the business rule
A GPA scale tops out below 10 → DECIMAL(3,2).
An age is a whole number → INT, not text.
A name may be Arabic → NVARCHAR, and remember the N'…' literal.
A type that is too narrow fails at insert time — after your application shipped.

Primary Key vs. Foreign Key

One identifies a row. The other points at a row in a different table.

PREDICT FIRST A foreign key must reference which kind of column in the parent table?
PRIMARY KEY identifies
▪Uniquely identifies each record in the table
▪Cannot contain NULL — enforced implicitly
▪A table has exactly one PK constraint
▪That one constraint may span several columns (composite)
composite primary key
PRIMARY KEY (StudentID, CourseID)
REFERENCES
FOREIGN KEY references
▪References a PK or eligible UNIQUE key in another table
▪Enforces referential integrity — the parent row must exist
▪May be NULL unless you add NOT NULL
▪A table may have many foreign keys
foreign key constraint
FOREIGN KEY (DepartmentID)    REFERENCES Departments(DepartmentID)
SAME COLUMN NAME, TWO ROLES Departments.DepartmentID → PK | Students.DepartmentID → FK | Same name, same type — different jobs.

Constraints and Data Integrity

A constraint is a rule the database refuses to break — even when the application has a bug.

TRAP QUESTION A column is declared Age INT CHECK (Age >= 16). Can a row still store NULL in Age?
PRIMARY KEYPK
Unique row identity. Implicitly NOT NULL.
StudentID INT PRIMARY KEY
FOREIGN KEYFK
The referenced parent row must exist.
REFERENCES Departments(DepartmentID)
NOT NULLREQUIRED
A value must be supplied. No blanks.
StudentName NVARCHAR(100) NOT NULL
UNIQUENO DUPLICATES
No two rows share a value. One NULL is allowed.
Email NVARCHAR(100) UNIQUE
CHECKRANGE
Value must satisfy a predicate. NULL passes.
Age INT CHECK (Age >= 16)
DEFAULTFALLBACK
Supplies a value when the column is omitted.
Grade INT DEFAULT 0
The fix
Age INT NOT NULL CHECK (Age >= 16)
Four distinct questions, four distinct constraints: who is this row (PK) · is the value required (NOT NULL) · is it unique (UNIQUE) · is it in range (CHECK) · does the parent exist (FK).

Understanding Relationships

Three shapes cover almost every schema you will design.

PREDICT FIRST A student takes many courses; a course has many students. How is this stored?
One-to-One
1 : 1
Enforced by a UNIQUE foreign key — so at most one child per parent.
One-to-Many
1 : ∞
The FK lives on the many side. This is our Students → Departments link.
Many-to-Many
∞ : ∞
Two one-to-many links into a junction table. Neither side stores the other's ID.
CARDINALITY
How many rows may participate — one or many.
OPTIONALITY
Must it participate? Expressed as NOT NULL (mandatory) or nullable FK (optional).
BUSINESS RULE, NOT GUESSWORK
Exact min/max participation comes from requirements and the constraints you can actually enforce.

Why Do We Need a Junction Table?

Because a many-to-many relationship cannot live in either table.

PREDICT FIRST PRIMARY KEY (StudentID, CourseID) in Enrollments prevents what?
How the many-to-many is resolved
Step 0 / 3
Why not just add a column?
A CourseID column in Students holds one value per row. A student with four courses would need four columns — and the fifth course would have nowhere to go.
Why these columns live here
EnrollmentDate — describes this student joining this course.
Grade — the result of that specific enrollment, not of the student in general.
The test: if an attribute needs both IDs to make sense, it belongs in the junction table.

Implementing Departments & Students

Dependency order is not a style preference — SQL Server enforces it.

PREDICT FIRST Why must Departments be created before Students?
02_departments_students.sqlT-SQL · SQL Server
CREATE TABLE Departments (    DepartmentID   INT PRIMARY KEY,    DepartmentName NVARCHAR(100) NOT NULL UNIQUE); CREATE TABLE Students (    StudentID    INT PRIMARY KEY,    StudentName  NVARCHAR(100) NOT NULL,    Email        NVARCHAR(100) NOT NULL UNIQUE,    Age          INT NOT NULL CHECK (Age >= 16),    DepartmentID INT NOT NULL,    FOREIGN KEY (DepartmentID)        REFERENCES Departments(DepartmentID));
Line by line
0 / 6
Departments created first. No FK yet, so it can be built independently.
DepartmentID INT PRIMARY KEY — unique identity, implicitly NOT NULL.
NOT NULL UNIQUE — every student needs a name; no two students share an email.
NOT NULL CHECK — the trap from slide 5: both are required to truly enforce an age.
DepartmentID INT NOT NULL — stores the reference; NOT NULL makes participation mandatory.
FOREIGN KEY … REFERENCES — only valid because Departments already exists.
FAILS
Creating Students first raises Msg 1769: Foreign key references invalid table — the dependency is real, not editorial.

Creating Courses & Enrollments

One column can be both a primary key and a foreign key at the same time.

PREDICT FIRST Which creation order is the only valid one?
03_courses_enrollments.sqlT-SQL · SQL Server
CREATE TABLE Courses (    CourseID   INT PRIMARY KEY,    CourseName NVARCHAR(100) NOT NULL,    Credits    INT NOT NULL CHECK (Credits BETWEEN 1 AND 6)); CREATE TABLE Enrollments (    StudentID INT NOT NULL,    CourseID  INT NOT NULL,    PRIMARY KEY (StudentID, CourseID),    FOREIGN KEY (StudentID)        REFERENCES Students(StudentID),    FOREIGN KEY (CourseID)        REFERENCES Courses(CourseID));
Two jobs, two mechanisms
0 / 4
Courses is a parent. It references nothing, so it can be created as soon as Departments and Students exist.
PRIMARY KEY (StudentID, CourseID) — the pair must be unique. Stops duplicate enrollments.
FOREIGN KEY (StudentID) — the student must exist in Students.
FOREIGN KEY (CourseID) — the course must exist in Courses. Two FKs, two different parents.
Two roles at once
StudentID is part of the PK
StudentID is also an FK → Students
The PK and the FK answer different questions. Neither replaces the other.

Referential Integrity & Delete Behavior

The database refuses to leave a reference pointing at nothing.

PREDICT FIRST An FK is enforced. You insert a row referencing a parent that does not exist. What happens?

NO ACTIONSQL Server default
The delete is blocked while dependent rows exist. Nothing is changed; you must deal with the children first.
CASCADEexplicit opt-in
The delete propagates — dependent rows are removed too. Powerful, and dangerous if the business rule does not say so.
DESIGN QUESTION, NOT A SYNTAX QUESTION
Should deleting a department erase its students? For this university, no — so we keep NO ACTION and handle students deliberately.
ON UPDATE is the same idea for key changes; NO ACTION is likewise the default.
